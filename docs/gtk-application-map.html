Who calls classInit?

Yes, on first construction it runs synchronously inside ExampleAppWindow.new(). Your new() calls native GObject through the bindings. GObject calls a binding-generated trampoline, which calls your classInit. There’s no event-loop dispatch in that chain.

Follow the call stack

Read indentation as “called by the line above it.” The two branches inside newInstance are sequential: registration returns before construction starts.

ExampleAppWindow.new(app)                         [your Zig]
└─ newInstance(ExampleAppWindow, …)                [Zig binding]
   ├─ 1. getGObjectType()                          [Zig binding]
   │  └─ g_type_register_static(…, &info, …)        [C: GObject]
   │     Saves the init function pointers. Returns a type ID.
   │     Does not call your classInit here.
   │
   └─ 2. g_object_new_with_properties(type ID, …)  [C: GObject]
      ├─ g_type_class_ref → g_type_class_get       [C: GObject]
      │  └─ type_class_init_Wm                     [if class not initialized]
      │     └─ Calls the registered f_class_init    [C → Zig]
      │        └─ Generated classInit trampoline   [Zig binding]
      │           └─ ExampleAppWindow.classInit     [your Zig]
      │              Saves the XML template + stack field offset.
      │
      └─ g_object_new_internal
         └─ g_type_create_instance                 [C: GObject]
            └─ Calls info.f_instance_init          [C → Zig]
               └─ ExampleAppWindow.instanceInit   [your Zig]
                  └─ gtk_widget_init_template      [C: GTK]
                     Builds the children and fills window.stack.

new() returns the initialized window. Your caller can now present it.

The trace omits parent initializers and other GObject bookkeeping. On a second new(), the type ID and class already exist: there’s no registration or classInit again, but instanceInit still runs for the new window. If something else initialized the class earlier, even the first new() skips class setup.

Where is the indirect call wired up?

In the bindings’ gobject2/ext.zig, defineClass puts its generated trampoline in f_class_init and your window initializer in f_instance_init. The trampoline calls userClassInit(class), where userClassInit is the callback you supplied as .classInit = &classInit. Native GObject invokes the stored pointers; it doesn’t look up Zig function names.

Native source: g_object_new_with_properties · class callback invocation · instance callback invocation.

Where does this happen relative to main() and run()?
main()
├─ ExampleApp.new()             → ExampleApp.classInit installs activate/open
└─ GApplication.run()
   └─ activate() or open()       → your override runs in the primary instance
      └─ ExampleAppWindow.new()  → runs the trace above, if a window is needed

The application and the window have separate classes. The application’s class initializer runs before run() on first construction; the window’s runs later, when its class is first needed.

01 / Responsibilities

The libraries and your code

Zig + the bindings

Your code chooses behavior. The bindings expose native functions and pass pointers and values between Zig and C. They are not another UI framework.

GLib + GIO

GLib provides the main loop, byte containers and utilities. GIO provides GApplication (application lifecycle and request routing) and GFile (a file reference you can read from).

GObject

Registers types, creates instances, manages references and supports signals and virtual methods. It calls initialization functions using the pointers the bindings registered.

GTK

Extends GIO’s application type with window management. It creates and lays out widgets, applies templates, and renders the widget tree. GDK is GTK’s window-system and input layer; niri is the Wayland compositor.

Build time: Nix supplies native GTK and pkg-config; the Zig bindings tell the build to link the native libraries. @embedFile("window.ui") embeds raw XML bytes. Runtime: GTK uses those bytes to initialize actual widgets. No GResource bundle is involved in this example.
02 / Request routing

One entry point, two paths

  1. Your Zig code
    main()

    Converts Zig’s arguments to C’s count and pointer array, creates ExampleApp, and calls run(). The -- belongs to zig build; it forwards what follows to the executable.

  2. Native GIO
    GApplication.run(argc, argv)

    Processes the arguments. With handles_open = true, positional file arguments become GFile objects. GIO dispatches the request to the primary instance (which might already be running).

No filenames → activatezig build run-application

ExampleApp.activate() creates and presents a window. The stack has no pages.

Filenames → openzig build run-application -- README.md build.zig

ExampleApp.open() reuses the active window if it can, otherwise creates one. It calls window.openFile(file) for each file, then presents the window.

Two separate decisions: handles_open tells GIO when to dispatch an open request. virtual_methods.open.implement(class, &open) tells it which function implements that request. The virtual method is a function pointer stored on the class, not a button signal you connected to an instance.
03 / Object construction

One shared recipe, separate children for every window

These are two callbacks inside the construction trace, not two functions that call each other. classInit configures the shared class; instanceInit populates the window now being created.

Two names, one binding

In bindTemplateChildFull("stack", 0, @offsetOf(ExampleAppWindow, "stack")), the first "stack" identifies the XML object. The second names the Zig field so the compiler can compute its byte offset. GTK gets the offset, not the Zig field name. 0 means not to expose the widget as a GtkBuilder internal child.

Two structs, two jobs

The class struct is shared and holds method slots. The instance struct holds one window’s state, including its own stack pointer. Each struct begins with its corresponding parent struct, letting GTK use the same address as the parent type.

Separate class initializers: ExampleApp.classInit installs the activate and open overrides. ExampleAppWindow.classInit installs the window template. Same kind of callback, different types and different jobs.

The template makes everything through the stack. openFile() creates each scrolled window and text view.

05 / Next tutorial: a menu

Who calls startup, and who calls Quit?

This is the next tutorial step, not part of the current Zig source. There are three separate chains: startup registers the actions, window initialization builds the menu, and user input invokes an action later.

main()
├─ ExampleApp.new()
│  └─ GObject → ExampleApp.classInit()       installs the startup override
└─ GApplication.run()
   └─ GIO registers this as the primary instance and emits startup
      └─ ExampleApp.startup()                your override
         ├─ Parent startup                 initializes GTK
         ├─ Add "preferences" and "quit" to the app's action map
         └─ Set Ctrl+Q → "app.quit"

Later, a window is created:
ExampleAppWindow.new()
└─ GObject → ExampleAppWindow.instanceInit()
   ├─ initTemplate()                        creates the GtkMenuButton
   └─ GtkBuilder loads menu.ui → setMenuModel() attaches the menu

Later, the user selects Quit or presses Ctrl+Q:
GTK resolves "app.quit" → the app's "quit" action
└─ GSimpleAction emits activate → your onQuit() → GApplication.quit()
   The main loop exits and run() returns.
The bridge is the action name. The XML does not name a Zig function. app.quit means “look up quit in the application’s action map.” Both the menu item and the shortcut point there. This action’s activate signal is not the application’s activate callback.
06 / Self-check

Predict what happens, then check

I launch with no filenames. Why is there no text?

GIO calls activate, not open. GTK creates the stack from XML, but openFile() never adds a page.

I create a second window. Do the windows share a stack?

No. They share one class template, but instanceInit makes a new stack for the second window. Each window’s stack field points to its own widget.

What if I set the template but never call initTemplate()?

The class has the recipe, but your window never builds the XML children. Binding stack does not create a stack by itself.

Is the Zig binding calling my open function?

GIO dispatches the request. The binding helped put the address of your function in the class’s virtual method slot; GIO calls it at runtime.
