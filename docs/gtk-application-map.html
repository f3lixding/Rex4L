Who calls what?

01 / Responsibilities

The libraries and your code

Zig + the bindings

Your code chooses behavior. The bindings expose native functions and pass pointers and values between Zig and C. They are not another UI framework.

GLib + GIO

GLib provides the main loop, byte containers and utilities. GIO provides GApplication (application lifecycle and request routing) and GFile (a file reference you can read from).

GObject

Registers types, creates instances, manages references and supports signals and virtual methods. It calls initialization functions using the pointers the bindings registered.

GTK

Extends GIO’s application type with window management. It creates and lays out widgets, applies templates, and renders the widget tree. GDK is GTK’s window-system and input layer; niri is the Wayland compositor.

Build time: Nix supplies native GTK and pkg-config; the Zig bindings tell the build to link the native libraries. @embedFile("window.ui") embeds raw XML bytes. Runtime: GTK uses those bytes to initialize actual widgets. No GResource bundle is involved in this example.
02 / Request routing

One entry point, two paths

  1. Your Zig code
    main()

    Converts Zig’s arguments to C’s count and pointer array, creates ExampleApp, and calls run(). The -- belongs to zig build; it forwards what follows to the executable.

  2. Native GIO
    GApplication.run(argc, argv)

    Processes the arguments. With handles_open = true, positional file arguments become GFile objects. GIO dispatches the request to the primary instance (which might already be running).

No filenames → activatezig build run-application

ExampleApp.activate() creates and presents a window. The stack has no pages.

Filenames → openzig build run-application -- README.md build.zig

ExampleApp.open() reuses the active window if it can, otherwise creates one. It calls window.openFile(file) for each file, then presents the window.

Two separate decisions: handles_open tells GIO when to dispatch an open request. virtual_methods.open.implement(class, &open) tells it which function implements that request. The virtual method is a function pointer stored on the class, not a button signal you connected to an instance.
03 / Object construction

One shared recipe, separate children for every window

  1. Your code → Zig bindings
    ExampleAppWindow.new(app) → newInstance(...)

    The binding calls getGObjectType(). On its first call, that function registers the type, parent type, struct sizes and callback pointers. It returns the type ID used to ask GObject to create the window.

  2. GObject → your callback / class setup
    classInit(class) → setTemplate(bytes)

    When GObject first initializes the window class, your callback gives GTK the XML recipe and registers a binding for the child named stack. No stack widget is created by this callback.

  3. GObject → your callback → GTK / each window
    instanceInit(window, …) → initTemplate()

    GTK applies the template to this particular window and creates its box, label and stack. It writes the stack widget’s pointer into this window’s stack field.

Two names, one binding

In bindTemplateChildFull("stack", 0, @offsetOf(ExampleAppWindow, "stack")), the first "stack" identifies the XML object. The second names the Zig field so the compiler can compute its byte offset. GTK gets the offset, not the Zig field name. 0 means not to expose the widget as a GtkBuilder internal child.

Two structs, two jobs

The class struct is shared and holds method slots. The instance struct holds one window’s state, including its own stack pointer. Each struct begins with its corresponding parent struct, letting GTK use the same address as the parent type.

Separate class initializers: ExampleApp.classInit installs the activate and open overrides. ExampleAppWindow.classInit installs the window template. Same kind of callback, different types and different jobs.
04 / Data and widgets

How a file becomes a page

Data flow

GFile (reference to a file)
  ↓ file.loadContents()
File bytes in memory
  ↓ view.getBuffer().setText(...)
GtkTextBuffer (holds the text)
  ↓ displayed by
GtkTextView (read-only widget)

Widget tree after opening a file

ExampleAppWindow
└─ GtkBox
   ├─ GtkLabel  “Loaded from window.ui”
   └─ GtkStack  (id="stack")
      └─ GtkScrolledWindow  (one per file)
         └─ GtkTextView

The template makes everything through the stack. openFile() creates each scrolled window and text view.

stack.addTitled() adds a page and gives it a title. GtkStack displays one page at a time but doesn’t provide tabs. A GtkStackSwitcher tied to that stack supplies the buttons; it’s not in the current tutorial XML. There’s no file picker in this example, either.

Why not just read the file in main? You can, for a standalone viewer. This tutorial takes the longer route to show how GIO can deliver file-open requests to an already-running app and how a GTK template can initialize a custom window type.
05 / Self-check

Predict what happens, then check

I launch with no filenames. Why is there no text?

GIO calls activate, not open. GTK creates the stack from XML, but openFile() never adds a page.

I create a second window. Do the windows share a stack?

No. They share one class template, but instanceInit makes a new stack for the second window. Each window’s stack field points to its own widget.

What if I set the template but never call initTemplate()?

The class has the recipe, but your window never builds the XML children. Binding stack does not create a stack by itself.

Is the Zig binding calling my open function?

GIO dispatches the request. The binding helped put the address of your function in the class’s virtual method slot; GIO calls it at runtime.
